# 知识库清理与重建设计

## 1. 背景

当前知识库存在三类已确认问题：

1. `GB/T 35273` 的旧 TXT 在 11.2 节中途截断；当前 PDF 提取文本较完整，但仍带有页眉、页码和目录噪声。
2. `GB/T 41391` 的 PDF 容器页由多页纵向拼接，部分页面包含旋转、密集表格；现有整页 OCR 已产生大量重复和与原文无关的文本，不能继续作为可信知识源。
3. 四份 PDF 在当前 Chroma 中各自仅形成一个超大 Chunk。现有切分器只识别“第 X 章/条”和 Markdown 规则，不能识别国家标准的 `1`、`3.1`、`A.1` 等层级。

因此，问题不只是文本“看起来不整洁”，而是提取可靠性、清洗可审计性、切分结构和入库安全性均需补强。

## 2. 目标与非目标

### 2.1 目标

- 对每个知识源建立可复核的页级清单和质量报告。
- 原生文本优先，OCR 只处理无可用文本的页面；异常长图先分段再 OCR。
- 保守删除确定性噪声，保留规范性条款、注释、示例、附录和表格内容。
- 支持国家标准数字章节、附录层级及超长条款的二次切分。
- 质量不合格的文档禁止进入 Chroma。
- 在新 Collection 中重建和验证，旧 Collection 在切换前保持不变。

### 2.2 非目标

- 不修改 Query Builder、Embedding、LLM、Prompt、CSV Pipeline 或数据库 Pipeline。
- 不对法规正文做摘要、改写或语义补全。
- 不为当前四份文档编写按文件名匹配的定向清洗规则。
- 不承诺把复杂表格恢复成与 PDF 完全一致的视觉布局；第一版保留其标题、表头、行列文字和来源位置。

## 3. 方案选择

采用“通用自动规则 + 异常页面专项提取 + 人工抽样门禁”的混合方案。

- 纯人工清洗准确但不可复现，后续新增法规成本高。
- 全自动清洗效率高，但无法可靠判断复杂表格 OCR 是否出现语义幻觉。
- 混合方案让常规页自动完成，把人工检查集中在空白页、异常长图、密集表格和质量指标超限页面。

## 4. 总体数据流

```text
原始 PDF/TXT（只读）
  → SourceInventory（哈希、页数、编码、页级状态）
  → 原生文本 / 分段 OCR
  → KnowledgeCleaner（正文 + 删除审计）
  → KnowledgeQualityGate（完整性、噪声、OCR、结构检查）
  → StandardChunker（章节、条款、附录、长度控制）
  → 候选 Chroma Collection
  → 固定查询回归 + 人工抽样
  → 配置切换或回滚
```

原始文件、OCR 原文、清洗文本、质量报告和向量库是不同层次的产物，不互相覆盖。

## 5. 组件设计

### 5.1 质量数据模型

新增 Pydantic 模型统一表达：

- `SourceManifest`：文件名、SHA-256、格式、页数、提取器版本。
- `PageQuality`：页码、来源方式、字符数、空白状态、分段数和异常项。
- `CleaningAudit`：规则名称、删除数量及少量定位样例，不保存整份重复正文。
- `KnowledgeQualityReport`：文档级指标、失败原因、`PASS/REVIEW/FAIL` 状态。

报告使用 JSON 保存到 `.runtime/knowledge_quality/<知识库版本>/`，不进入 Git。

### 5.2 PDF 提取与异常长图分段

保留现有“原生文本可用则直接提取”的路径。对需要 OCR 的页面：

- 普通比例页面沿用逐页 OCR。
- 高宽比异常的长图，通过水平低墨迹带识别页面间隔，切为多个阅读片段。
- 每个片段单独 OCR，再按容器页和片段顺序合并。
- OCR 提示明确要求逐字转录、保留表格结构、不可解释或补充；无法辨认使用 `?`。
- 记录容器页、片段序号和 OCR 缓存键，方便定位回原图。

分段依据图像结构而非文件名，因此可用于后续同类扫描件。`GB/T 41391` 的现有异常缓存应通过提取器版本变更自然失效，不能手工覆盖原缓存。

### 5.3 保守清洗

`KnowledgeCleaner` 接收带页边界的提取结果，执行以下通用规则：

- 删除跨多页高频出现、且位于页首或页尾的相同页眉页脚。
- 删除独立页码、OCR 页标记、纯装饰分隔线和多余空白。
- 删除完全相同且异常重复的 OCR 行；表头重复只标记，不跨页盲目删除。
- 识别目录区域并从检索正文中排除，但在报告中记录目录是否存在。

规则不得删除含规范性语义的行。每项删除均写入 `CleaningAudit`，同时保留清洗前 OCR 缓存以供回查。

### 5.4 质量门禁

质量状态定义：

- `PASS`：可自动入库。
- `REVIEW`：文本可用，但存在需人工抽查的异常页；确认后方可入库。
- `FAIL`：缺页、正文截断、严重重复、OCR 无关输出或空白页无法解释，禁止入库。

第一版硬性门禁：

- PDF 页必须逐页记录为“有文本”或“确认空白”，不能无状态缺失。
- 非空白正文页不得为空。
- 单一重复行不得出现于正文行的 20% 以上；超限进入 `REVIEW`。
- 单页字符数超过文档页字符中位数的 8 倍时进入 `REVIEW`。
- 必须识别到正文起始章节；声称含附录的文档必须识别到附录。
- `GB/T 41391` 因已发现严重 OCR 异常，首次重建必须人工核对首页、普通正文页、旋转表格页、密集表格页和末页后才能由 `REVIEW` 转为 `PASS`。

最后一条是文档验收要求，不是分类或清洗规则硬编码。

### 5.5 国家标准结构化切分

在现有 Chunker 中新增识别：

- 一级章节：`1 范围`、`2 规范性引用文件`。
- 多级条款：`3.1`、`5.2.3`。
- 附录及附录条款：`附录 A`、`A.1`。
- 表、注和示例作为当前条款的组成部分。

每个 Chunk 包含 `document_name`、`version`、`chapter`、`article`、`page_start`、`page_end`、`source_sha256` 和稳定 `chunk_id`。超长条款按段落二次切分，目标长度 800–1600 个字符，最大 2000 个字符，相邻子块保留约 150 个字符重叠；不得在条款标题与正文之间切断。

### 5.6 版本化重建

重建脚本先完成全部加载、清洗、质量检查和切分，再写入候选 Collection：

```text
data_classification__<knowledge_base_version>
```

任何文档为 `FAIL` 或未经批准的 `REVIEW` 时，命令失败且不修改当前 Collection。候选库通过数量、长度分布和固定查询回归后，仅通过配置切换 Collection 名称；旧库保留用于回滚。

## 6. 针对现有文档的处理结论

| 文档 | 首次处理重点 | 入库条件 |
|---|---|---|
| GB/T 35273 | 使用完整 PDF 提取，停用截断 TXT；清除页眉页码目录 | 正文延伸至后续章节、附录及参考文献 |
| TC260 分类分级指引 | 清除页标、页码和目录噪声 | 40 页状态完整、条款切分正常 |

## 7. 测试与验收

### 7.1 自动测试

- 清洗规则不会删除正文中的条款号、规范性措辞和表格文字。
- 长图分段只在满足比例和低墨迹分隔条件时触发，顺序稳定。
- 数字章节、附录和超长条款切分符合边界及长度要求。
- `FAIL/REVIEW` 文档不能写入候选 Collection。
- 重建失败时原 Collection 的名称和内容不变。
- 现有 TXT、Markdown 规则和普通 PDF 加载测试继续通过。

### 7.2 文档级验收

- 四份 PDF 都产生 manifest、清洗文本、审计日志和质量报告。
- `GB/T 35273` 不再使用截断 TXT。
- `GB/T 41391` 不再出现已发现的无关长段文本和大面积重复。
- 四份法规不再各自只有一个超大 Chunk，且没有 Chunk 超过 2000 字符。
- 候选库导入报告列出来源数、Chunk 数、长度分布和失败项。
- 使用固定检索问题对比新旧库，人工确认来源和条款定位不退化。

## 8. 风险与控制

- **误删正文**：仅使用位置、高频和行形态联合判定；保留删除审计和原始缓存。
- **OCR 幻觉**：缩小单次识别图像、设置异常指标、复杂表格强制人工抽查。
- **切分过碎**：以条款为首选边界，只对超长条款二次切分。
- **重建破坏现有实验**：候选 Collection 独立创建，验收后才切换配置。
- **外部 OCR 调用成本**：缓存以源文件哈希、模型、提示版本和分段版本共同寻址，只重跑失效页面。

## 9. 实施边界

实施期间只修改知识提取、清洗、质量校验、切分和重建相关模块及测试。正式清洗产物和 Chroma 数据保持 Git 忽略；设计、实现代码、测试和固定的小型夹具进入 Git。
